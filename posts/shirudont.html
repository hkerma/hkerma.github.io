Shirudon’t? Surviving unpatched vulnerabilities and the hype around them

November 24, 2026

Research can be cruel. You spend years building your skills, your knowledge, you get a novel idea, you implement it and evaluate it. Then, right before you submit, you find out someone else published something addressing the same problem a few weeks earlier. It’s always been the game; sometimes you win and sometimes you don’t.

One thing I always try to keep in mind is the end goal of my research: making itself useless. In an ideal world, I am useless: the OS is safe, the industry isn’t trying to gain a few microseconds for loading the latest memes (at the cost of introducing major vulnerabilities), and everything runs correctly and securely. In this ideal world, vulnerabilities don’t need patching, because they don’t exist, and I’m out of a job; I can go back to playing guitar.

Today, I feel useless, not because we finally live in my ideal world, but because the work of careful, cautious researchers like myself is being drowned out by “AI-accelerated” projects that ship faster and shout louder.

I work on “surviving unpatched vulnerabilities”. More than three years ago, my group and I became interested in the following problem: patching a vulnerability can take weeks, while exploitation can happen much sooner. Keep in mind that this was before the current wave of AI, and the gap was already obvious. So I built Phoenix [1]: it helps users identify the sequence of system calls an exploit relies on, and apply a temporary mitigation until the official patch is released and applied. Phoenix isn’t perfect. It can be racy, it needs a kernel module, and it is a research prototype. I built it without AI assistants, learning and writing everything myself. Still, projects like Phoenix have never been more relevant, because AI agents can accelerate the discovery and exploitation of vulnerabilities.

Yesterday, Cisco and OpenAI announced Shirudo [2], which targets a similar problem. So, obviously I browsed the code (with Claude’s help to find my way through thousands and thousands of LOC) and read its documentation. The people behind it are some of the most accomplished BPF developers in the kernel community, so my expectations were really high. That’s also why I am so disappointed by the gap between their claims and the reality.

No restart needed? The headline demo doesn’t show what the headline says.The demo claims to block an exploit in Elasticsearch “without a restart” [3]. Shirudo’s documented signed Java-upatch mechanism, however, only configures agents for JVMs that start later, and its automatic environment configuration only reaches JVMs launched by a systemd user manager started after the shield is loaded [4]. The Java agent can also attach dynamically to an already-running JVM, but that path uses the standard Java Attach API: the code does not route it through Shirudo’s signed-upatch verification, nor record the attachment in its measurement register. The demo reports attaching to a running Elasticsearch process but does not explain how the JAR was delivered or verified. So, as far as the public material shows, the headline “no restart” result went through the one path that skips Shirudo’s own signing and measurement. Attaching a Java agent to a running JVM is something you could already do without Shirudo; making that step signed and measured is the whole point of the project. I know “no restart” is an important problem: most of Phoenix’s design was built around that constraint.

Most of the shipped CVE shields watch rather than protect, and the ones that block are blunter than what already exists.Three of the five named kernel-CVE package definitions in the repository are detectors. The two others aim to block operations associated with Copy Fail (CVE-2026-31431) [8]. One refuses every new AF_ALG socket; the other refuses zero-copy splices into AF_ALG sockets, including legitimate ones. The latter leaves ordinary copying sends available, but neither distinguishes an attack from benign use. Disabling the affected algif_aead module is an existing, narrower mitigation when it is built as a module and can be removed; existing BPF LSM mitigations can also block the affected interface without a reboot.

It can’t run on any kernel you have today.Shirudo requires a development kernel (bpf-next) with five extra patches, including new LSM and TPM hooks, plus TPM 2.0. That’s fine: it’s a work in progress! But getting these changes upstream will require kernel review, and BPF signing has already been the subject of debate [5].

Verified is not the same as protected.The announcement says shields can be verified “even if an attacker has gained administrator access” [6]. But verifying a shield is not the same as ensuring it remains active: the project’s own threat model says that root can apply a published and signed unload directive, or load older signed versions [7].

The fixes so far look like whack-a-mole.The code is moving very fast: GitHub shows about 1,800 commits [2]. The project also carries new kernel hooks to close ways around its protections. How much control do the developers actually have over the tool, its vision, the problem it solves? If every newly found way around a security mechanism requires another kernel hook, we call it “whack-a-mole”, and that’s not a good sign.

Don’t get me wrong, this does not make Shirudo useless; I am sure it’s a promising prototype, and I will follow its development closely. But overselling a security tool is not harmless: it convinces people the problem is solved, and they stop looking. That is how vulnerabilities live on.

When I started doing research, I was beaten by people smarter than me, and I could live with that. But now, it feels like volume and reach win over actual contributions. Whoever ships the most and announces the loudest sets the story, whether or not the problem is solved. I see the same pattern far beyond cybersecurity, in politics and in economics. In the end, I am very grateful for such projects to appear, especially when they are sponsored by major companies like Cisco: it gives me very strong material to cite in the “limitations of existing solutions” paragraph of my next paper.
